# Agent guide — سانس‌یار (Sansyar)

Read this before writing code. `PROMPT.md` is the full build brief (with the phase map in §۰.۵) and `DESIGN_SYSTEM.md` is the locked visual contract. If a change contradicts either, update the doc in the same change.

## What this is

A Persian, RTL booking app for futsal-hall **سانس** (slots). One hall manager publishes sessions; players open a shared link inside the **Eitaa** messenger and register. The app runs **only as an Eitaa mini app (برنامک)** — a plain browser gets the gate overlay.

There is **no SMS panel, no OTP code and no `/login` page**, and login is never tied to a number: Eitaa `initData` is the only way in. The one number in the product is `User.phone` — the player's **contact number**, asked once on the first run by a blocking sheet whose only action is Eitaa's own `requestContact` (typed entry was removed by the owner's rule: a player who does not send the number cannot use the app), stored on the account, **immutable afterwards** and rendered **to the manager only**. The same first-run flow then asks for the **real name pair** (`User.firstName`/`lastName`), stored separately from the Eitaa display name and just as immutable. The contact payload is a signed string and is verified server-side exactly like `initData` (`src/lib/eitaa-contact.ts`) — never make the number an identity, never verify it by SMS, never treat the contact data as a login (Eitaa's rules forbid that).

Approval is about the **person, once** (the owner's newest round): a fresh account is born `PENDING`, sees only the «درخواستت ثبت شد» waiting screen and can do nothing — no board, no session page, no seat — until the manager approves it from `/admin`; after that a seat it asks for is `CONFIRMED` outright (a full hall puts it in `WAITLIST`). A rejection is **not final**: `/admin` keeps a «ردشده‌ها» list and one tap takes the account back. The important events — membership approval/rejection, waitlist promotion, late-cancel penalty — are also sent as Eitaa messages (`src/lib/eitaa-notify.ts`).

## Next.js 16 conventions (breaking vs. older versions)

- **`middleware.ts` no longer exists — it is `proxy.ts`** (`export function proxy(request)`), and it runs on the Node.js runtime. Never treat it as the only auth boundary: re-verify inside every server action.
- **Request APIs are async**: `await cookies()`, `await headers()`, `params` and `searchParams` are **Promises**.
- **Typed route helpers are global**: `LayoutProps<"/">` (used by the root layout), `PageProps<…>` for pages — generated per real route, never hand-written.
- **`next lint` is gone** — the script is plain `eslint`.
- **`revalidateTag(tag, profile)` takes two arguments**; `updateTag` and `refresh()` exist for read-your-writes.
- Dev output goes to `.next/dev`.
- **Cache Components is ON** (`cacheComponents: true` + `partialPrefetching: true` in `next.config.ts`). This is deliberately kept:
  - Data access is **dynamic by default**; opt into caching with `'use cache'`.
  - The static shell is served immediately and dynamic parts **stream** in.
  - **Runtime data (`cookies()`, `headers()`, DB reads) must be inside a `<Suspense>` boundary**, otherwise the build fails. Design every screen as *static chrome + Suspense'd data with a skeleton whose row rhythm matches the real rows*.
  - Do not add `runtime = 'edge'`; Cache Components requires Node.

## Layout & routing

- `src/app/layout.tsx` — `<html lang="fa" dir="rtl">`, font import, metadata/viewport, `<EitaaRuntime>` (owns the splash, the preload login and the gate overlay), `TooltipProvider`, `Toaster`. Nothing else.
- `src/app/(app)/` — player/manager surfaces; `(app)/layout.tsx` wraps screens in `<AppShell>` (sticky header + fixed bottom tab bar) and mounts the **three** blocking first-run overlays — `PhoneGate` (its only action is Eitaa's `requestContact`), `RealNameGate` (the immutable real-name pair, asked right after the phone) and `MembershipGate` (the manager's one-time decision on the account: `PENDING` sees the waiting screen + «دوباره چک کن», `REJECTED` gets its own sentence — the app stays unusable behind both, and both retire locally the moment `checkMembership()` answers `APPROVED`; phone first, then the real name, so the queue the manager reads carries both). All three are server-render-safe (`null` until client-ready), so the static shell is unaffected. Screens: `(app)/page.tsx` (the session board, `?tab=open|soon|past`), `(app)/my/page.tsx` (the player's ledger: pay link, cancel control and the `WAITLIST` state with its «از لیست انتظار دراومدی» chip), `(app)/profile/page.tsx` (identity + «موجودی من» — the wallet card with its paged ledger, `getMyBalance` + `?balancePage=` — + «آمار من» + «سابقهی من» + «خلاصهی قوانین» + «تغییر نام» — the display name only; the phone and the real name are read-only), `(app)/sessions/[id]/page.tsx` (session detail + registration + cancel + the numbered roster + the balance hint and the «حضوری فقط … بده» door sentence, with its own nested `not-found.tsx`), `(app)/sessions/[id]/pay/page.tsx` (the mock gateway) and `(app)/rules/page.tsx` (**قوانین** — the written rules: «پول و موجودی» first, then the live cancel rules read from `Setting`, attendance and membership; linked from the profile and the session page's rules card, titled in `nav.ts`).
- `src/app/admin/` lives outside `(app)` and is the manager's whole panel (phase ۶): its own layout — header + a sticky `AdminNav` section strip (`src/components/layout/admin-nav.tsx`, driven by `ADMIN_SECTIONS` in `nav.ts`) + the same bottom `TabBar` — so **no screen inside `/admin` ever needs Eitaa's BackButton**: every section stays one tap away (the owner's rule). Screens: `page.tsx` the **dashboard** (four stat tiles — ثبت‌نام امروز · سانس بعدی با اشغال · دریافت‌نشدهی ۳۰ روز اخیر · محروم فعال — above the intact membership queue: «در انتظار تأیید» + «ردشده‌ها»، `listMembershipQueue()` + `MembershipButtons`), `sessions/` (list + `/new` + `/[id]` + `/[id]/edit` — the roster carries the per-seat money split), `users/` (+`/[id]` — the **balance card**: the number, «تغییر موجودی» (`adjustBalance`) and the paged `BalanceEntry` ledger under `?balancePage=`), `venues/` (+`/new` + `/[id]/edit`) and `settings/`. There is **no `(public)` group and no `/login` route**.
- **Every list that can grow pages in the database** (the owner's rule: no screen may render an unbounded history): one contract in `src/lib/pagination.ts` (`PAGE_SIZE = 20`, `parsePage`/`pageRange`/`clampPage`) + the shared server-rendered `Pagination` (`src/components/admin/pagination.tsx`, page number in the URL next to the list's own filters). The public past window is two weeks — `HOME_LOOKBACK_DAYS = 14` in `src/lib/sessions.ts`: the board shows players only the last two weeks, `/my` reads one page of its «گذشته» segment at a time (newest first), and the manager's full archive is the paginated `/admin/sessions` («برگزارشده»).
- The two wallet ledgers ride the same contract: `/admin/users/[id]` pages an account's `BalanceEntry` rows for the manager, `/profile` pages the player's own, both under `?balancePage=` — the shared `Pagination` learned a `pageParam`, so a second pager on one screen can never overwrite the first.
- The **"only inside Eitaa" gate is not a route**: it is a client overlay rendered by `EitaaRuntime` when `initData` is empty or rejected — HTTP 200, no redirect, and it sets `document.documentElement.dataset.runtime = "outside"`.
- **Every route group has an error boundary**: `src/app/error.tsx` (root), `(app)/error.tsx`, `admin/error.tsx`, plus `src/app/global-error.tsx` (which brings its own document, font and tokens). All render the one shared `AppError` (`src/components/common/app-error.tsx`) with Next 16's `retry()` and a way home — a thrown screen never falls through to the framework's English page, and the `(app)`/`admin` boundaries keep their shells (header, tab bar, section strip), so a crash is never a dead end.
- `src/components/layout/nav.ts` is the **single source of truth** for the tab bar, the header title and the Eitaa BackButton. Don't hardcode routes in components.

## Design rules that are easy to get wrong

- **Never use the fill yellow as a bare mark on white** (`#F5B301` is 1.85:1). Icons, rails and markers use `--brand-mark` (#B57F00) or `--brand-ink` (#8A6100). Yellow fill always carries **ink** text.
- **Hairlines are structure, not elevation** (`--line` #DDE2D7 is deliberately quiet). Anything that *is* an affordance (input outlines, primary dividers) uses `--line-strong` (#75817A).
- **Cards earn elevation from `shadow-card`**, not from a drawn border.
- **Numerals are proportional, never tabular.** Estedad's tabular set pads every digit to the widest glyph (12.94px against 5.73–12.52px at 17px/700), so `tabular-nums` — and the old `.tnum` utility that carried it — swelled clocks by 39% («۲۱:۳۰» 56.17px → 40.53px) and Jalali dates by 42%. CSS `letter-spacing` cannot buy the gap back (engines refuse to track Arabic-script digit runs), so there is no tracking knob: the figure set is the only lever. `globals.css` §Numerals has the measurements and neutralizes the Tailwind utility (unlayered `font-variant-numeric: normal`) so the banned class can never bite; Tailwind still emits it only because these very comments name it. Nothing in the app is a numeric column, and the ticking `LiveCountdown` is a sentence.
- No dark mode, no glass, no gradients, no hero sections. The mini app keeps fixed light chrome and ignores `themeChanged`.
- Colour is never the only cue: every status pairs colour with an icon or a word.
- Persian copy: verb-first, one label per intent, no filler; all user-facing numbers go through `toPersianDigits`/`formatToman`; dates render Jalali in `Asia/Tehran` while **storage is always UTC**.
- **Register is semi-formal, second person singular**: «تو»، «بزن»، «میگیری»، «ثبتنامت لغو شد». Never «شما / کنید / میشود / لطفاً» in user-facing text, and never a customer-service voice («کاربر گرامی»). Labels stay noun-phrases (`لغو ثبتنام`), sentences carry the outcome. Fixed vocabulary (`DESIGN_SYSTEM.md` §۲) is exempt — a status word is never replaced for tone.
- Any colour change requires re-running `npm.cmd run check:contrast` (28 pairs, AA).

## Environment

Copy `.env.example` → `.env`. Variables: `DATABASE_URL`, `SESSION_SECRET`, `ADMIN_EITAA_ID` (comma-separated allowed), `APP_URL`, `EITAA_BOT_TOKEN`, `EITAA_APP_USERNAME`, `EITAA_LINK_TEMPLATE`, `EITAA_DEV_LOGIN`, `EITAA_DEV_BOT_TOKEN`.

The **dev-only login simulator** is gated on `NODE_ENV === 'development'` + `EITAA_DEV_LOGIN` and must be fully inert in production. Surfaces: a «ورود آزمایشی بازیکن / مدیر» panel on the gate (and on the profile for sign-out), `window.__eitaaDebugLogin(initData)` — and `__eitaaDebugLogin("reject:<پیام>")`, which renders the gate's «ورودت تأیید نشد» story (the one phase a plain browser can never reach) — plus the CLI `npx.cmd tsx scripts/eitaa-sign-initdata.ts`: it loads `.env` through `@next/env`, so an escaped `\$` reads exactly as the server reads it. Its code and its copy are also **absent from a production bundle** — the dev-only modules are reached through a compile-time `NODE_ENV` guard (see Gotchas). The **phone simulator** is the sibling: `devContact` (`src/server/actions/dev-contact.ts`) signs a *real* contact payload with the same bot token, the first-run sheet's dev box and `window.__eitaaDevContact` feed it through the real `savePhoneFromEitaa` (signature check included), and it re-checks `EITAA_DEV_LOGIN` before doing anything.

## Database

Prisma 7 is not the Prisma you know — three things will bite:

- **A driver adapter is mandatory.** `new PrismaClient()` without one throws at construction. `src/lib/db.ts` wires `@prisma/adapter-mariadb`, which speaks the MySQL wire protocol, so MySQL 8 and MariaDB both work. Scripts running outside Next (e.g. `prisma/seed.ts`) build their own client, because `src/lib/db.ts` is marked `server-only`.
- **Configuration lives in `prisma7.config.ts`** — that exact file name; the CLI looks for it. It holds the datasource URL *and* the seed command. `package.json#prisma` is gone, and `schema.prisma` has no `url`, so `DATABASE_URL` is read by both the CLI and the app and they cannot drift apart.
- **The generated client is source code**, at `src/generated/prisma` (git-ignored, eslint-ignored). Run `npm.cmd run db:generate` after any schema change — a fresh clone cannot typecheck or build before it.
- **Every seat write passes the membership gate, and seat allocation is a locking read, not a COUNT-then-INSERT race.** `registerSeat` (`src/server/registration-core.ts`) runs `SELECT id FROM \`Session\` WHERE id = ? FOR UPDATE` inside the transaction, then the ban check, then a **raw locked read of the user row** (`SELECT membershipStatus FROM User … FOR UPDATE`) — so a manager's decision and the account's own registration serialize on one row — then the session stage, the existing row, and finally it counts rows: **occupancy is `CONFIRMED`**, and a fresh registration is `CONFIRMED` when there is room and `WAITLIST` otherwise (`@@unique([sessionId, userId])` is the second line of defence; P2002 → «قبلاً برای این سانس ثبت‌نام کردی.»). An account that is not `APPROVED` is refused with `NOT_APPROVED` before a row is ever written. Capacity is always a `count()` — never a counter column on `Session`. The **membership engine** is `src/server/membership-core.ts` (`decideMembership`: locks the user row, re-reads the status under it; approve from `PENDING`/`REJECTED`, reject from `PENDING` only, `ALREADY_APPROVED`/`NOT_PENDING`/`NOT_FOUND` otherwise) and the freed seat side is `cancelSeat`, which promotes the earliest `WAITLIST` row (ordered by `createdAt`, then `id`) **straight into `CONFIRMED`** with `promotedAt` — there is no second approval for a seat. Both cores are client-injected and clock-injected on purpose: `registerForSession` (`src/server/actions/registration.ts`), `cancelRegistration` (`cancel.ts`), `approveMembership`/`rejectMembership`/`checkMembership` (`membership.ts`) are only shells (zod + signed session + `revalidatePath` + refusal copy + the fire-and-forget Eitaa messages), and `scripts/check-registration-race.ts` drives the *same* functions against a throwaway fixture — `npm.cmd run check:race` walks the whole story: the membership gate (pending/rejected refused with no row, approve → the next tap is a seat, re-approve of a rejected account, `ALREADY_APPROVED`/`NOT_PENDING`/`NOT_FOUND`), a decision raced against the account's own registration and approve × reject raced on one account, 30 concurrent registrations at a capacity-12 session (exactly 12 `CONFIRMED` / 18 `WAITLIST` with dense queue positions), a 60-call double-tap wave (every duplicate → `ALREADY`, never a raw P2002), releases and promotions, cancel races, the late-cancel warning/ban story and the guards (`CLOSED`/`STARTED`/`NOT_REGISTERED`/`BANNED`-before-the-gate).
- **Attendance is its own locking engine** (`src/server/attendance-core.ts`, phase ۵; shell in `src/server/actions/attendance.ts`). A mark is `PRESENT | LATE | ABSENT` plus `lateMinutes` (1–720, `LATE` only): the transaction locks the registration row (`FOR UPDATE`) and the guards answer in order — `NOT_FOUND` → `SESSION_CANCELED` → `SESSION_NOT_PUBLISHED` → `NOT_CONFIRMED` (a waitlist row never entered the hall) → `NOT_STARTED` → `INVALID`. `ABSENT` writes one `NO_SHOW` `Penalty` when `noShowEnabled`; a `LATE` past `lateThresholdMinutes` runs the strike ladder (`floor(qualifying lates / lateStrikeCount)`, counted as *events* inside the window, so a manager's pardon never hands a strike back). Re-marks and marks after a pardon are no-ops — no automatic penalty deletion on a correction, the manager waives the row. `closeAttendance` locks the session and sweeps only `{CONFIRMED, PENDING}` rows → `ABSENT`, once (idempotent). The engine is client- and clock-injected like the others; `npm.cmd run check:attendance` (57 checks) walks the whole story against a throwaway fixture (`attcheck_*` ids — it must not run next to `check:race` or `db:seed`).
- **The wallet is its own engine too** (`src/server/balance-core.ts`, the balance round; shells in `src/server/actions/admin-balance.ts` and the money paths of `registration.ts`/`cancel.ts`/`payment.ts`/`admin-session-manage.ts`). The owner's rule: money paid for a seat that is given up lands on the account's **balance — never in cash** — and the next registration spends it automatically before asking for money. Three writers, one contract: `chargeSeatFromBalance` (called by `registerSeat`/`promoteFromQueue` when a row becomes the player's — a fresh `CONFIRMED` seat, a revival, a promotion; a `WAITLIST` row spends nothing), `refundSeatToBalance` (every release: player cancel, manager removal, whole-session cancel — `cancelRefundToman` is the one formula the dialog and the engine share: a `PAID_*` row returns its whole `amountToman`, an `UNPAID`/`WAIVED` row only its `paidFromBalance`, a waitlist row zero) and `adjustBalanceByAdmin` (the manager's manual ±, `INSUFFICIENT` on an overdraw — the balance is never zeroed by a failed move). Every movement writes one `BalanceEntry` row, so the ledger always adds up to the column. **Lock order is session → user, and `lockBalances` sorts the user ids ascending** before a transaction touches more than one wallet — a waiter is found *before* the locks (`findNextWaiter` then `promoteFromQueue`), because two mirrored cancels would otherwise deadlock. A seat write must always state `amountToman` (no default — the snapshot is mandatory), and `npm.cmd run check:balance` walks the whole money story against a throwaway `balcheck_*` fixture.

Datetimes are UTC; Prisma maps `DateTime` → MySQL `DATETIME(3)`. `prisma/seed.ts` is idempotent (every write is an `upsert`) and **anchored to today** in Tehran wall-clock, so re-running it refreshes the demo window instead of leaving sessions in the past.

## Domain map

- `User` — `eitaaId` (String, `@unique`, up to 52 bits), `name` (the **display name** — the Eitaa name, or the one the player set via «تغییر نام»), `role` (`USER` | `ADMIN`), `membershipStatus` (`PENDING | APPROVED | REJECTED`, default `PENDING` — **the membership gate**: only an `APPROVED` account may register; the manager's decision lives in `src/server/membership-core.ts`) + `membershipDecidedAt` (its stamp; a fresh `USER` is approved by the manager once, and an `ADMIN` is auto-approved on login), `firstName`/`lastName` (the **real name pair**, asked once right after the phone and immutable — the name the manager checks against the person at the door), `phone` (String?, nullable — the contact number, normalized to `09XXXXXXXXX` by `src/lib/phone.ts`; sent once by Eitaa's `requestContact` through the mandatory first-run sheet, **immutable afterwards** (only a manager can fix it, in the DB), admin-visible only, never an identity), `balance` (Int, default 0 — the **wallet**: money returned from a canceled seat lands here, the next registration spends it automatically, and only `src/server/balance-core.ts` writes it; it never goes negative). Admin identity comes from `ADMIN_EITAA_ID` — re-granted on every login — and a DB `ADMIN` row is honoured too: a login **promotes, never demotes** (`upsertUser` in `src/server/eitaa-login.ts`), so the seeded demo manager keeps its panel; revoking is a deliberate DB write. Membership is never downgraded by a login either. A placeholder name the seed wrote («مدیر سانس») is swapped for the real Eitaa name on the first login; a name the person edited is never touched.
- `Venue`, `Session` (slot: venue, start/end UTC, capacity, price, registration window, payment mode, nullable per-session overrides of the cancel rules, and `mapUrl` — the manager's Neshan link, which wins over the venue's own link; when both are empty the page falls back to a Neshan search on the address, `src/lib/neshan.ts`), `Registration` (status — `CONFIRMED | WAITLIST | CANCELED`, where **occupancy is `CONFIRMED` alone** — no default on the column: every writer states it; `amountToman` — the **price snapshot** of the moment the seat was taken, the one source every money line and every refund reads, so a later price edit never re-prices an old seat; `paidFromBalance` — the part the wallet covered (`paymentStatus: PAID_BALANCE` when it covered all of it); + waitlist order + payment state + attendance + `promotedAt`, the promotion stamp: a row that came off the waitlist **into the hall**, behind the screens' «از لیست انتظار دراومدی» — cleared by every fresh registration/revival), `Penalty` (a warning when `days = 0`, a ban otherwise — manual bans included), `Setting` (single row `id = 1` of editable rules).
- Profile reads/writes: `getPlayerStats` (`src/server/player-stats.ts` — the four tiles), `updateDisplayName`, `saveRealName` and `savePhoneFromEitaa` (`src/server/actions/profile.ts`) — the writes on that screen, all validated by the shared rules in `src/lib/phone.ts` / `src/lib/format.ts`. The number has **no write path of its own any more** (typed entry was removed): `savePhoneFromEitaa` is its only producer, and it refuses to change a number the account already carries (`LOCKED`). «شناسهی من» is a bootstrap affordance: it renders only while `ADMIN_EITAA_ID` is empty or for the admin themself.
- `BalanceEntry` — the wallet's ledger: signed `amount` (positive credits, negative takes), `balanceAfter` (the standing right after the movement, so a row explains itself), `type` (`REGISTRATION_DEDUCT | CANCEL_REFUND | ADMIN_ADJUST`), optional `note`, and the `session`/`registration`/`byAdmin` it came from. One row per movement; both ledgers render the shared `BalanceLedgerRow`.
- `Attendance` and `Ban` have **no tables of their own**: attendance is columns on `Registration`, and a ban is a `Penalty` row with `days > 0`.
- No `OtpCode` model. Ever.

## Gotchas

- **`cn` must be imported from `@/lib/utils`, never from the `cn` package.** The package's stock merge tables classify our custom `--text-*` sizes (`text-h1`, `text-button`, …) as *colours*, so `cn("text-white", "text-button")` silently deletes the colour (it rendered ink-on-red at 2.6:1 until phase 0 caught it). `src/lib/utils.ts` registers the scale via `createCn`. After `npx shadcn add`, run `npm.cmd run fix:cn-imports`.
- **A `$` in `.env` is eaten by dotenv-expand.** Next.js loads `.env` through dotenv-expand, so a bare `$NAME` in a value becomes "" when `NAME` is undefined. `EITAA_BOT_TOKEN="…knak$AoKC-D…"` loaded **5 characters short** (159 vs 164) and every `initData` HMAC comparison would have failed with no visible cause. Escape it as `\$NAME`. `npm.cmd run check:env` scans `.env`/`.env.example` and fails on unescaped `$NAME` (warns on `${NAME}`, which is deliberate interpolation).
- **`initData`: the second HMAC key is the raw digest, not its hex string.** `secret = HMAC-SHA256(key="WebAppData", message=bot_token)` may be `.digest()` (**bytes**) and that buffer is the key of the second HMAC. Feeding `.digest("hex")` back in yields a *plausible but wrong* mac (`19ec4dfd…` instead of the official `c3bb1efc…`) that fails every login with no other symptom. `scripts/check-eitaa-signature.ts` pins the implementation to the official vector.
- **The contact payload is the same signed shape as `initData` — verify it, never trust it.** `WebApp.requestContact` hands back `key=value&…&hash=<hex64>`; `verifyContact` (`src/lib/eitaa-contact.ts`) reuses `src/lib/eitaa-signature.ts` (one HMAC recipe, never a second copy), enforces `auth_date` with the same 24h rule, and extracts the number **tolerantly** because Eitaa documents no key names: `phone_number`/`phone`/`contact`, then any value `normalizePhone` accepts — identifiers (`user_id`, `id`, `auth_date`, `user`) are skipped, so an id can never be stored as a phone. The requester id is compared with the signed-in account when the payload carries one (`user_id`, `sender_user_id`, or an id inside `user`/`contact` JSON — a bare top-level `id` is ignored on purpose: an ambiguous key would refuse *valid* numbers). Refusals log parameter **keys only** — the payload carries a personal number. `CONTACT_DEADLINE_MS = 30_000` in `src/components/eitaa/sdk.ts` ends a native sheet that never answers, and there is **no typed fallback at all**: the gate retries the same Eitaa action, so the number can only ever come from Eitaa.
- **Cache Components fails the build on request-time values.** An uncached database read, `new Date()`, `Date.now()` or `Math.random()` anywhere in a prerendered route errors with `blocking-prerender-current-time` — even inside `<Suspense>`. Do both: wrap the work in `<Suspense>` **and** `await connection()` (from `next/server`) before it. See the `SessionPage` → `SessionDetailScreen` pair in `src/app/(app)/sessions/[id]/page.tsx`; the build then reports the route as `◐ Partial Prerender`.
- **The gate must return HTTP 200 with no redirect** (EitaaYar's destination URL cannot 30x). It is an overlay from `EitaaRuntime`, not a page or a route — nothing to redirect, no layout to add.
- **Never set `X-Frame-Options` or CSP `frame-ancestors`** — Eitaa web loads mini apps in an `<iframe>`.
- The Eitaa SDK (`https://developer.eitaa.com/eitaa-web-app.js`) is the **only** external script, and the **bridge loads it** (`ensureEitaaSdk` in `src/components/eitaa/sdk.ts`) — *not* `next/script`: `strategy="beforeInteractive"` puts the tag inside the RSC tree, React hydration then fails ("A tree hydrated but some attributes of the server rendered HTML didn't match"), the client tree stays inert and the splash never advances. The bridge injects the identical tag itself (guarded so it is added once) and the screen is capped by `DETECTION_DEADLINE_MS = 4500`, after which the gate shows — so the splash can never hang. Login must still complete **before** app content renders (the server-rendered splash overlay is only removed once `eitaaLogin` resolves). Never trust `initDataUnsafe`, and never treat `window.Eitaa` as proof of being inside Eitaa: the script loads in a plain browser too, so the only "we are inside" signal is a **non-empty `initData`**.
- **A one-shot `useRef` guard around a boot effect breaks in dev.** React 19 mounts effects twice; the first pass is cancelled and the second returns early, so the splash hangs forever. Keep the boot idempotent instead of guarding it — see `EitaaRuntime`.
- **`AppShell` must never be handed `isAdmin={false}`.** Its prop default is `undefined` on purpose: `TabBar` then falls back to the role in the Eitaa bridge context (`isAdmin ?? user?.role === "ADMIN"`), so «مدیریت» appears the moment the verified session says ADMIN while every `(app)` route keeps its static shell. A literal `false` wins over the context and silently hides the manager tab forever.
- **Cancel is a locking read too, and the dialog and the engine share one verdict.** `cancelSeat` (`src/server/registration-core.ts`, called by `cancelRegistration` in `src/server/actions/cancel.ts`) locks the session row (`FOR UPDATE`) before it reads anything, then resolves the rules (`resolveCancelRules(setting ?? DEFAULT_CANCEL_RULES, session)`) and calls `cancelVerdictNow` — the *same* helper the confirm dialog used, so the sentence the player confirmed is the sentence the engine writes. A `WAITLIST` row is **always free** — `waitlistCancelVerdict()`, no `Penalty` row at all, wherever the clock is — because nobody in line ever entered the penalty engine (the hall was already full, so leaving frees nothing and promotes nobody). Otherwise the freed seat promotes the earliest `WAITLIST` row (ordered by `createdAt`, then `id`, so a tie is deterministic) **straight into `CONFIRMED`** with `promotedAt` — the hall, not a queue — and exactly one `Penalty` row is written per late event: none for `FREE`/`LATE_PARDONED`, `days: 0` for the first-in-window warning, `days: lateCancelPenaltyDays` otherwise. The first-time forgiveness counts **events** (`LATE_CANCEL` rows inside the window), not un-waived bans: a manager's pardon must not hand the warning back. `listMyRegistrations(userId, now)` and `getSessionDetail(id, viewerId, now)` take the screen's clock so a ban card and a cancel verdict can never disagree about "now".
- **Money is a wallet: a seat given up returns its money to the balance, never to cash.** (the balance round) Every release — the player's own cancel (late or not), the manager's removal, a whole-session cancel — lands the seat's money on `User.balance`, and the next registration (even in person, even a waitlist promotion) spends it automatically before asking for the rest. A `WAITLIST` row still owes nothing («تا جات نشه پرداختی لازم نیست» — `NOTHING_OWED_YET` in `src/lib/sessions.ts`): it spends nothing while it waits and refunds nothing when it leaves, because it never held a seat. The dialog, the player's row and the door sentence all read the same numbers (`cancelRefundToman`/`seatMoneyLabel`/`inPersonRemainderNote` in `src/lib/balance.ts`) from the seat's **snapshot** — `amountToman` minus `paidFromBalance` — never from `session.priceToman`, which a price edit may have moved since the seat was taken. Payment still never gates a seat: the seat is `CONFIRMED` before the gateway, `payForRegistration` is a compare-and-set, and paying never re-checks capacity — so a paid seat can never be told «ظرفیت پر».
- **Payment is a compare-and-set, not a read-then-write.** `payForRegistration` (`src/server/actions/payment.ts`) flips the seat with an `updateMany` whose `WHERE` already carries the state (`status: CONFIRMED, paymentStatus: UNPAID`), so two taps can never both "charge" and `count === 0` is the honest `ALREADY_PAID`; a still-waitlisted row is refused with «تو لیست انتظار هستی — تا جا آزاد نشه، پرداختی لازم نیست.» The gateway asks for the seat's own **outstanding** money (`max(0, amountToman − paidFromBalance)`): zero outstanding is `ALREADY_PAID`, and a seat the wallet settled whole lands `PAID_BALANCE`, which `isPaidSeat` counts as paid and the manager's payment select refuses to overwrite (`FROM_BALANCE` — the row renders a chip, not a select). The `/sessions/[id]/pay` screen only *states* the state, and a fresh registration **never** lands on it (a full hall means `WAITLIST`, so there is nothing to pay): the pay CTA appears on the confirmed row.
- **Eitaa program → player messages are `POST https://eitaayar.ir/api/app/sendMessage`** with `{ token, chat_id, text }` in the JSON body (`src/lib/eitaa-notify.ts`); the `/api/{token}/sendMessage` shape answers 401. Sending is free but spends the program's **daily message credit**, delivery needs the player to have pressed «شروع» on the program at least once, and every refusal is swallowed and logged (`[notify] …`) — a message may fail and that is fine. Dev servers and the race harness **log instead of sending** (`IS_PRODUCTION` gate in the notifier), so no automated run can message a real person. The message builders live in that one module (every sentence in one home) and are called **from the action shells only** (`membership.ts`, `cancel.ts`) — `registration-core.ts` must never import it, or the tsx harness would drag `server-only` in.
- **The membership gate is an overlay, and the server never trusts the client about it.** `registerSeat` re-reads `membershipStatus` under a row lock, so a hand-made request from a `PENDING`/`REJECTED` account is refused with `NOT_APPROVED` (the copy differs per state: `MEMBER_PENDING` / `MEMBER_REJECTED`, both in `registration-core.ts`); the client overlay (`MembershipGate`) only decides *what the person sees*. `checkMembership()` is a server action because the bridge is a client component and the queries are `server-only`. A `REJECTED` account is not finished: the manager re-approves it from `/admin`'s «ردشده‌ها» list, and the gate retires the moment the check answers `APPROVED`. The first-run order is fixed — phone sheet → real-name sheet → this gate — so the queue the manager reads always carries a real name and a contact number.
- **Never nest an action inside a row's link.** A `<Button>` inside the `<Link>` of a `/my` row is invalid HTML and swallows taps, so the row is `<li>` + `<Link>` (the reading part) + an action row underneath — still inside one hairline group.
- **`/sessions/[id]/pay` also exports `instant = false`** — the same `CLIENT_HOOK_DYNAMIC` reason as its parent segment; the build still reports it `◐`.
- **The Neshan link shapes are inferred.** The manager's own link wins (a `https://neshan.org/maps/share/<lat>,<lng>` share link or an `nshn.ir` short link), then the venue's link, then `/maps/search/<address>` — that last one is a guess about the web app's own routing (it serves the PWA shell for any path). Verify on a device, exactly like `?startapp=`.
- **Android draws a button under a message when the link carries `&btn=` — everywhere else the link is the way in.** The message API has no markup and the web/desktop clients render no button, but Eitaa **Android** shows a button under any message whose app link has the param, labelled with the **raw** value — it is never percent-decoded, so the label must stay Persian text and must never be `encodeURIComponent`d (a percent-encoded label shows up literally as `%D8%…`; verified on the owner's device, مهر ۱۴۰۵). Eitaa's own `@trendingapps` posts and its survey link use the same param. `buildAppLink` (`src/lib/eitaa-link.ts`) appends `&btn=ثبت‌نام` to every start-param link; the share copy may name the button, and the link must still ride in the message. The «دکمه» fields in the EitaaYar panel remain the card inside the program's own chat.
- **Deep links are built in `src/lib/eitaa-link.ts` only**; the `?startapp=` shape follows Eitaa's own «ارسال داده به برنامک» example and was verified live (the link serves Eitaa's app landing page with `et://resolve?…&startapp=…`) — the open-behavior still gets a real-device check. `parseStartTarget` accepts ids of 6–64 chars and `s_<id>` maps to `/sessions/<id>`, which exists as of phase ۳. The bridge still asks `canOpenSession` (a server action, because the bridge is a client component and the queries are `server-only`) **before** navigating, so a stale link lands on the board with a «سانس مورد نظر پیدا نشد» toast instead of a 404 (§۱۳.۶).
- **A dynamic route plus URL-reading chrome is the one case a prerendered shell cannot cover.** `AppHeader`, `TabBar` and the bridge read `usePathname()`, and a dynamic segment has no pathname while its shell is prerendered, so instant-navigation validation fails the build with `CLIENT_HOOK_DYNAMIC`. `/sessions/[id]` therefore exports `instant = false` (Next's own documented remedy: it disables that validation only — the route still streams its Suspense'd data and still reports `◐`). The bridge additionally reads the pathname in `PathnameWatcher`, inside a `<Suspense>`, so the root layout can never block a future dynamic route. Do not "fix" this by rendering the chrome without an active tab on every route.
- **Chrome freezes timers in a hidden tab.** With `document.visibilityState === "hidden"` (minimized window, background tab) `setTimeout`/`setInterval`/rAF do not fire, so the splash's 4.5s deadline and the SDK polling stall and the app sits on «در حال ورود…» forever. The bridge nudges itself on `visibilitychange`/`focus`/`pageshow`, but an automated check must either keep the window visible or drive the login directly with `window.__eitaaDebugLogin(initData)` (dev only, timer-free). The same throttling defers React's streamed Suspense holes — a fresh navigation can sit on its skeleton indefinitely — so verify request-time screens over HTTP (the server HTML/stream) and use the hidden tab only for click-driven checks after a debug login.
- **A tunnel needs `allowedDevOrigins` *and* `experimental.serverActions.allowedOrigins`** — `*.trycloudflare.com` is registered in `next.config.ts` for both. Without the first one the dev server answers **403** to its own `/_next/*` assets whenever the request carries the tunnel's Origin: the HTML (and the splash) paints, no JS ever runs, and the screen sits on «در حال ورود…» forever — identically in a plain browser and inside Eitaa. Server actions are origin-checked the same way *in production too*, so `eitaaLogin` would be refused behind the tunnel even from a production build. Device tests therefore run against the **production** server on `:3000` (`next start -p 3000` after a green build; assets are minified — ~29 KB vs. ~890 KB in dev), with the dev server moved to another port when both are needed.
- **The dev simulator is not in a production bundle** (the phase-۸ hygiene item, proved by grepping `.next/static`). Every dev-only surface — the gate's panel, both console hooks and the phone sheet's box — lives in its own module (`src/components/dev/dev-login-panel.tsx`, `dev-console.ts`, `dev-panel-slot.tsx`, `src/components/profile/phone-dev-box.tsx`) and is reached **only** through a compile-time `process.env.NODE_ENV !== "production"` guard (`next/dynamic(…, { ssr: false })`, or a guarded bare `import()` inside an effect): a static import anywhere puts the code and its Persian copy straight back into the release, and the server's simulators (`dev-auth.ts`/`dev-contact.ts`) become unreferenced with it. The guard is hygiene, never a security boundary — `devEnabled`/`EITAA_DEV_LOGIN` and the re-checks inside `devLogin`/`devContact` remain the real gate, and the runtime checks must stay *in addition* to it (`EITAA_DEV_LOGIN=0` in dev must still hide the panel, so the guarded module is only ever a lazy loader of the UI).
- Windows/PowerShell: use `npm.cmd` and `npx.cmd` (the `.ps1` shims are blocked by execution policy).
- **Never rewrite source text through PowerShell `Get-Content`/`Set-Content`.** `Get-Content -Raw` reads UTF-8 as CP1252 on this machine, so a round-trip double-encodes every Persian string into mojibake *and* still type-checks and builds green — it only shows up as garbled text in the browser. Use the editor tools, or Node with an explicit `'utf8'` encoding.
- This workspace is a git repo (created when the Render deploy work started): `main` is the base branch and the Render deploy work lives on the `render-deploy` branch.

# سانس‌یار

وب‌اپ فارسی و راست‌چین ثبت‌نام **سانس**‌های سالن فوتسال: مدیر سانس منتشر می‌کند و بازیکن‌ها از روی یک لینک مشترک در **ایتا** ثبت‌نام می‌کنند.

سانس‌یار **فقط به‌صورت برنامک (Mini App) داخل پیام‌رسان ایتا** اجرا می‌شود؛ باز کردن همان آدرس در مرورگر عادی فقط گیتِ «سانس‌یار فقط از داخل ایتا باز می‌شود» را نشان می‌دهد (کد ۲۰۰، بدون ریدایرکت). ورود یکپارچه با حساب ایتاست — `initData` امضاشده + اعتبارسنجی سمت سرور — و **هیچ کد پیامکی، هیچ ورودی بر پایه‌ی شماره و هیچ مسیر ورود جایگزینی وجود ندارد**. تنها شماره‌ی محصول، **شماره‌ی همراهِ خودِ بازیکن** است که یک‌بار در اولین اجرا و **فقط از خودِ ایتا** (`requestContact`؛ پیلود امضاشده سمت سرور) گرفته می‌شود — بدون هیچ راه دستی — روی حساب ذخیره می‌شود، **بعد از ثبت قابل تغییر نیست** و فقط مدیر می‌بیندش؛ هیچ نقشی در ورود ندارد. همان اولین اجرا بلافاصله بعد از شماره، **نام و نام خانوادگی واقعی** را می‌پرسد (جدا از نام نمایشی ایتا و غیرقابل‌تغییر)، و تا وقتی **مدیر عضویت حساب را تأیید نکند** بازیکن هیچ کاری نمی‌تواند بکند — فقط صفحه‌ی «درخواستت ثبت شد» را می‌بیند. تأیید **یک‌بار روی حساب** انجام می‌شود؛ بعد از آن هر ثبت‌نام تازه مستقیم قطعی است (سالن پر → لیست انتظار). رد شدن پایان کار نیست: مدیر از «ردشده‌ها» در `/admin` می‌تواند دوباره تأیید کند؛ تصمیم مدیر و رویدادهای مهم با **پیام خودِ برنامک در ایتا** خبر داده می‌شوند.

> راهنمای کامل پلتفرم (ایتایار، SDK، لینک اشتراک، دیپ‌لینک) در `.opencode/skills/eitaa-miniapp/SKILL.md` و نقشه‌ی فازها در `PROMPT.md` §۰.۵ است.

## پیش‌نیازها

- Node.js 20+ و npm — روی ویندوز همیشه `npm.cmd` / `npx.cmd` (شیم‌های `.ps1` اجرا نمی‌شوند)
- Docker برای MySQL 8.4 (یا هر MySQL/MariaDB محلی)
- فایل `.env` ساخته‌شده از `.env.example`

## راه‌اندازی

```powershell
npm.cmd install
npm.cmd run db:up          # MySQL 8.4 روی 3306 (docker-compose.yml)
npm.cmd run db:generate    # کلاینت Prisma 7 — بعد از هر تغییر اسکیما هم لازم است
npm.cmd run db:migrate
npm.cmd run db:seed        # داده‌ی دموی فارسی؛ idempotent و «امروزمحور»
npm.cmd run dev            # Turbopack → http://localhost:3000
```

باز کردن `http://localhost:3000` در مرورگر، طبق انتظار، گیتِ بیرون‌ایتا را نشان می‌دهد. برای رد شدن از گیت در توسعه، از پنل «حالت توسعه» روی همان گیت استفاده کن (بخش بعد).

## محیط (`.env`)

مقادیر کلیدی: `DATABASE_URL`، `SESSION_SECRET`، `ADMIN_EITAA_ID` (چند شناسه با کاما)، `APP_URL`، `EITAA_BOT_TOKEN` (فقط سرور)، `EITAA_APP_USERNAME`، `EITAA_LINK_TEMPLATE`، `EITAA_DEV_LOGIN`، `EITAA_DEV_BOT_TOKEN`. فهرست کامل با توضیح هر مورد در `.env.example` آمده است.

نکته: در مقدارهای `.env` هر `$` باید به‌صورت `\$` فرار داده شود (dotenv-expand وگرنه تا وقتی متغیر تعریف نشده باشد آن را با رشته‌ی خالی عوض می‌کند)؛ `npm.cmd run check:env` همین را چک می‌کند.

## ورود آزمایشی (فقط توسعه)

وقتی `NODE_ENV=development` و `EITAA_DEV_LOGIN` روشن است:

- روی گیت، پنل «ورود آزمایشی بازیکن / مدیر» را بزن؛
- یا در کنسول مرورگر: `window.__eitaaDebugLogin("<initData>")`؛
- یا با CLI یک `initData` امضاشده بساز:

```powershell
npx.cmd tsx scripts/eitaa-sign-initdata.ts --id 200000001 --name "کاربر آزمایشی" --start s_seed_session_past_older
```

(شناسه‌ی سانس باید معتبر باشد: `parseStartTarget` فقط شناسه‌های ۶ تا ۶۴ کاراکتری را می‌پذیرد، پس `s_1` بی‌صدا به خانه برمی‌گردد.)

همه‌ی این مسیرها از همان action واقعی و همان اعتبارسنجی سرور عبور می‌کنند. در production نه دکمه، نه هوک و نه action شبیه‌ساز وجود دارد — و کد و متن فارسی شبیه‌ساز هم اصلاً وارد باندل کلاینت نمی‌شود: ماژول‌های dev فقط از پشت یک گاردِ زمان‌کامپایل (`process.env.NODE_ENV !== "production"`) ایمپورت می‌شوند، پس باندلر همان‌جا حذفشان می‌کند و غیبتشان با یک گرپ ساده روی `.next/static` قابل بررسی است.

حسابی که شماره‌ی همراه ندارد، بعد از ورود یک شیتِ یک‌باره می‌بیند: تنها اکشن «فرستادن شماره با ایتا» است (`WebApp.requestContact`؛ پیلود امضاشده سمت سرور مثل `initData` تأیید می‌شود) — بدون راه دستی — و در dev جعبه‌ی شبیه‌ساز همان مسیر واقعی را تمرین می‌دهد (نه ورود، نه تأیید پیامکی). بعد از شماره، شیت دوم نام و نام خانوادگی واقعی را می‌پرسد و بعد از آن، تا تأیید مدیر، شیت سوم («درخواستت ثبت شد — منتظر تأیید مدیر باش») روی اپ می‌ماند. حساب‌های دمو شماره دارند؛ «مهدی توکلی» (`200000005`) عمداً بدون شماره است و مدیرِ seed هم — وقتی `ADMIN_EITAA_ID` خالی باشد — بدون شماره ساخته می‌شود. با همان‌ها می‌توانی شیت‌های اولین اجرا را تست کنی؛ «فرهاد بهرامی» (`200000017`) و «سجاد قربانی» (`200000018`) در انتظار تأیید و «کامران یوسفی» (`200000019`) ردشده‌اند تا صف `/admin` خالی نباشد.

## شناسه‌ی مدیر

بعد از اولین ورود، تا وقتی `ADMIN_EITAA_ID` تنظیم نشده باشد، «پروفایل ← شناسه‌ی من» شناسه‌ی ایتای تو را با دکمه‌ی کپی نشان می‌دهد؛ همان را در `ADMIN_EITAA_ID` بگذار و سرور را ری‌استارت کن تا تب «مدیریت» باز شود. بعد از آن بلوک «شناسه‌ی من» فقط برای خودِ مدیر دیده می‌شود — بازیکن عادی کاری با آن ندارد.

## ساختار مسیرها (وضعیت فعلی)

- `(app)/` — چیدمان بازیکن/مدیر با هدر چسبان و تب‌بار ثابت: `/` (تابلوی سانس با تب‌های «در حال ثبت‌نام / به‌زودی / گذشته»)، `/sessions/<id>` (جزئیات سانس + ثبت‌نام/لیست انتظار + لغو ثبت‌نام؛ فهرست ثبت‌نامی‌ها با **شماره‌ی ترتیب** در دو بخش «ثبت‌نام‌شده‌ها / لیست انتظار» و برای **مدیر** کنار هر نام لینک تماس `tel:`)، `/sessions/<id>/pay` (درگاه آزمایشی پرداخت — فقط روی ردیف قطعی)، `/my` (ثبت‌نام‌های من + وضعیت «قطعی»/«لیست انتظار» و چیپ «از لیست انتظار دراومدی» + پرداخت/لغو هر سطر؛ بخش «گذشته» با `?page=`)، `/profile` (پروفایل: آمار، سابقه، تغییر نام نمایشی، و «شماره‌ی همراه» و «نام واقعی» فقط-نمایش)
- `/admin` — **پنل کامل مدیر** با گارد سرور: نوار بخش‌ها («داشبورد / سانس‌ها / کاربران / مکان‌ها / تنظیمات») به‌همراه همان تب‌بار پایین، پس هیچ صفحه‌ای در پنل بن‌بست نیست و به دکمه‌ی بازگشتِ ایتا نیاز ندارد. داشبورد چهار تایل دارد (ثبت‌نام امروز، سانس بعدی با ظرفیت، دریافت‌نشده‌ی ۳۰ روز اخیر، محروم فعال) بالای صف عضویت — «در انتظار تأیید» (نام واقعی + شماره‌ی تماس با لینک `tel:` + زمان شمسی؛ تأیید/رد با پیام ایتا) و «ردشده‌ها». صفحه‌ها: `/admin/sessions` (لیست فیلتردار و **صفحه‌به‌صفحه** + «سانس جدید») و `/admin/sessions/<id>` (مدیریت سانس: حضور و غیاب، وضعیت پرداخت، حذف ثبت‌نام، ارتقای دستی از لیست انتظار، «بستن حضور و غیاب»، «لغو کل سانس» و «اشتراک‌گذاری سانس» با پیام آماده) و `…/<id>/edit`؛ `/admin/users` (جست‌وجو + چیپ‌های عضویت + پرونده‌ی کاربر با «محروم کردن/لغو محرومیت»)؛ `/admin/venues` (ساخت/ویرایش مکان)؛ `/admin/settings` (۱۲ قاعده‌ی پیش‌فرض با پیش‌نمایش زنده)
- گیتِ «فقط داخل ایتا» **route نیست**؛ overlay کلاینتی است که `EitaaRuntime` وقتی `initData` خالی باشد نشان می‌دهد
- `?tab=` تابلوی سانس را می‌چرخاند (تب «گذشته» فقط **دو هفته‌ی اخیر** را نشان می‌دهد؛ آرشیو کامل در پنل مدیر است)؛ `?startapp=s_<id>` (دیپ‌لینک اشتراک) به `/sessions/<id>` می‌رود؛ فهرست‌های بلند `?page=` دارند (صفحه‌ی ۲۰تایی) و دفترهای موجودی (`/profile` و `/admin/users/[id]`) `?balancePage=`

## برنامک ایتا (خلاصه)

- SDK رسمی `https://developer.eitaa.com/eitaa-web-app.js` تنها اسکریپت خارجی پروژه است و **خودِ پل** آن را تزریق می‌کند (`ensureEitaaSdk`)؛ هرگز با `next/script strategy="beforeInteractive"` لودش نکن (هیدریشن React را می‌شکند و اسپلش معلق می‌ماند) و هرگز لوکال هاست نکن.
- اعتبارسنجی `initData` سمت سرور انجام می‌شود، با **بایت خامِ** دیجست `HMAC-SHA256("WebAppData", bot_token)` به‌عنوان کلید HMAC دوم (رشته‌ی hex آن جواب نمی‌دهد).
- لینک اشتراک سانس فقط از `src/lib/eitaa-link.ts` ساخته می‌شود؛ شکل `?startapp=` مطابق مستندات خود ایتا («ارسال داده به برنامک») است و زنده تأیید شد. هر لینک سانس `&btn=ثبت‌نام` هم دارد: کلاینت **اندروید** با همین پارامتر زیر پیام یک دکمه می‌سازد (برچسب خام فارسی، نه درصدی — روی دستگاه تست شد)؛ وب و دسکتاپ دکمه‌ای نمی‌سازند و همان لینک تپ‌کردنی است.
- پیام‌های برنامک ← بازیکن (`src/lib/eitaa-notify.ts`) از `POST /api/app/sendMessage` با توکن سرور و `chat_id = eitaaId` می‌روند؛ فقط رویدادهای مهم (تأیید/رد عضویت، ارتقا از لیست انتظار، جریمه)، مصرف از اعتبار پیام روزانه، و در dev فقط لاگ می‌شوند.
- ثبت در ایتایار: آدرس مقصد HTTPS و **بدون ریدایرکت**؛ «عنوان دکمه / آدرس دکمه / عکس شروع / پیام شروع» کارتِ خودِ برنامه را می‌سازند که **داخل گفتگوی برنامه** دیده می‌شود (یک‌بار برای همیشه، نه per-message). زیر پیام‌های گروه/کانال، **اندروید** برای لینک‌های دارای `&btn=` دکمه می‌سازد و وب/دسکتاپ فقط لینک `?startapp=` را دارند — ورودی همه، همان لینک است. جزئیات کامل در اسکیل `eitaa-miniapp` و `PROMPT.md` §۱۳.

## وضعیت فازها

فازهای ۰ تا ۴ کامل‌اند و دو دور به‌درخواست مالک پیاده شده است — «شماره‌ی همراه/نام واقعی» و «تأیید عضویت». آنچه امروز کار می‌کند: تابلوی سانس با سه تب («در حال ثبت‌نام / به‌زودی / گذشته») و نشانگر شمارش کنار هر برچسب، صفحه‌ی هر سانس (مکان و آدرس + «مسیریابی در نشان»، زمان شمسی، قیمت و شیوه‌ی پرداخت، قوانین انصراف همان سانس، فهرست **شماره‌دار** ثبت‌نام‌شده‌ها و لیست انتظار با نشان «تو»)، ثبت‌نام تراکنشی با قفل ردیف سانس — **دروازه‌ی عضویت**: تا مدیر حساب را تأیید نکند کاربر فقط صفحه‌ی «درخواستت ثبت شد» را می‌بیند و سرور هم هر درخواست دستی او را رد می‌کند؛ بعد از تأیید، ثبت‌نام تازه **مستقیم قطعی** است (سالن پر → لیست انتظار) — تأیید/رد عضویت از `/admin` با **پیام ایتا**، **لغو شدن یک صندلی آن را مستقیم به نفر اول لیست انتظار می‌دهد**، شمارش معکوس باز شدن پنجره‌ی ثبت‌نام، کارت محرومیت فعال در «ثبت‌نام‌های من»، **لغو ثبت‌نام با «قانون همان لحظه»** (آزاد / اخطار اول / محرومیت؛ لغو از لیست انتظار همیشه آزاد و بدون ارتقا)، **درگاه آزمایشی پرداخت** (`/sessions/<id>/pay`) با ثبت اتمیک پرداخت — فقط برای ردیف قطعی و هنوز پرداخت‌نشده — **شماره‌ی همراه حساب** (شیتِ یک‌باره‌ی اولین اجرا، فقط از ایتا و غیرقابل‌تغییر + لینک تماس فقط برای مدیر) و **نام و نام خانوادگی واقعی** (شیت دوم، جدا از نام نمایشی)، و پروفایل با **آمار شخصی** (رفته / پیش رو / تاخیر / غیبت)، **سابقه‌ی جریمه‌ها** و **تغییر نام**. ارقام همه‌جا متناسب‌اند (بدون `tabular-nums`) و `npm.cmd run check:race` دروازه‌ی عضویت، بی‌مسابقه‌بودن ثبت‌نام هم‌زمان، ارتقاها و مسابقه‌های لغو را ثابت می‌کند.

**فاز ۵ (حضور و غیاب)** هم کامل است: مدیر روی صفحه‌ی هر سانس برای هر صندلی «حاضر / تاخیر (دقیقه) / غایب» می‌زند — با قفل ردیف و «یک‌بار برای هر رویداد»؛ غایب جریمه‌ی `NO_SHOW` می‌گیرد، تاخیرِ بالای آستانه در نردبان شمرده می‌شود و «بستن حضور و غیاب» بقیه‌ی صندلی‌ها را یک‌جا غایب می‌کند (بی‌خطر حتی با چند بار زدن). بازیکن نتیجه را در چیپ همان ردیف و «سابقه‌ی من» می‌بیند؛ `npm.cmd run check:attendance` (۵۷ بررسی) کل این داستان را ثابت می‌کند.

**فاز ۶ (پنل مدیریت)** هم تحویل شده: داشبورد، CRUD کامل سانس‌ها با پیکر شمسی و قوانین اختصاصی هر سانس، مدیریت یک سانس (حضور و غیاب/پرداخت/حذف/ارتقا/لغو کل/اشتراک‌گذاری)، پرونده‌ی کاربران با محروم/لغو، مکان‌ها و تنظیمات دوازده‌قاعده‌ای. سه قاعده‌ی مالک هم اعمال شده: تب «گذشته»ی عمومی فقط دو هفته، آرشیو کامل مدیر صفحه‌به‌صفحه (۲۰تایی)، و پنل بدون نیاز به دکمه‌ی بازگشتِ ایتا.

**دور تازه — «موجودی حساب» (کیف پول)** هم اضافه شده: پولِ صندلی‌ای که لغو شود به **موجودی حساب** برمی‌گردد (نقدی برنمی‌گردد) و ثبت‌نام بعدی — حتی حضوری — اول از موجودی خرج می‌کند و فقط مانده را می‌خواهد («حضوری فقط … بده — همین رو به مدیر نشون بده»)؛ مدیر از `/admin/users/[id]` موجودی را کم/زیاد می‌کند (هر حرکت یک ردیف «گردش موجودی» + پیام ایتا) و صفحه‌ی «قوانین» (`/rules`) همه‌ی این قواعد را برای بازیکن نوشته است. موتور `src/server/balance-core.ts` با قفل مرتب چند-کاربری (session → user) و اسنپ‌شات قیمت هر صندلی (`Registration.amountToman` / `paidFromBalance`) کار می‌کند و `npm.cmd run check:balance` (۱۱۵ بررسی) کل داستان پول را ثابت می‌کند.

**فاز ۸ (پولیش + چک‌لیست پذیرش)** هم انجام شد: مرز خطای هر گروه (`error.tsx` گروه‌ها + `global-error` با فالکِ مشترک «مشکلی پیش آمد» و دکمه‌ی «دوباره امتحان کن»)، حالت‌های خالی یک‌دست، کپی گیت برای «ورودت تأیید نشد» (وقتی داخل ایتایی ولی تأیید ورودت نمی‌شود)، خطای فرم‌ها و ۴۰۴ها در یک شکل، اندازه‌ی متن خواندنی `/rules`، پیل فعالِ نوار بخش‌های مدیر روی ۳۷۵px — و **کد و متن فارسی شبیه‌ساز dev دیگر داخل باندل production نیست** (گاردِ زمان‌کامپایل؛ غیبتش با گرپِ `.next/static` ثابت شده).

باقی‌مانده‌ی فاز ۷ فقط تأییدهای روی دستگاه واقعی است — باز شدن `?startapp=` داخل ایتا، دکمه‌ی `&btn=` روی ایتا اندروید و شکل لینک نشان — جزئیات در `PROMPT.md` §۰.۵.
